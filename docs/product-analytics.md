# Продуктовая аналитика AI Media Client

Статус: проект интеграции. На 29 сентября 2026 года события из AI Media Client **не отправляются**. Сервис PostHog разворачивается отдельно из передаваемого архива; включать сбор можно только после приёмки сервиса и обновления [политики данных](../public/legal/privacy.html).

## Зачем и как это работает

Первый этап посвящён только продуктовой аналитике. Self-hosted PostHog принимает явно названные события, сохраняет их в собственном ClickHouse и предоставляет воронки, удержание, когорты и панели. PostgreSQL AI Media Client остаётся источником истины для заказов, задач и кредитов. Логирование и ClickStack рассматриваются отдельно позже. PostHog hobby-развёртывание не имеет гарантий поддержки; эксплуатацию, обновления и восстановление берём на себя.

```text
После будущей интеграции:
Браузер после согласия ──→ фасад AI Media Client ──→ API сервера ──→ PostHog
Серверная транзакция ──→ PostgreSQL + outbox ──→ доставщик ──→ PostHog
                                                          │
                                            UI и Query API / ClickHouse
```

PostHog находится на отдельном хосте. Администратор открывает `https://<домен-аналитики>` через разрешённую сеть/VPN и входит под собственной учётной записью PostHog. Домен, учётные записи, проект, ключ проекта и политика доступа задаются при развёртывании; ключ проекта не является административным API-токеном. Не давать аналитическому агенту права записи. Сырой ClickHouse не публиковать в интернет.

## Как пользоваться панелями

После развёртывания создать в PostHog отдельный project для production и, при необходимости, для staging. В настройках production отключить autocapture и session replay. До появления продуктовых событий проверить только синтетическое `analytics_smoke`, затем удалить тестовые данные или исключить это событие из всех отчётов.

1. **Воронка до первой успешной генерации.** В разделе Product analytics → Funnels добавить по порядку `landing_viewed`, `studio_opened`, `login_completed`, `generation_submitted`, `generation_completed`. Для последнего шага фильтр `outcome=success`. Выбрать «уникальные пользователи», окно конверсии, например 7 дней, и сохранённую панель «Первое успешное создание». На первом шаге учитывать только посетителей, давших согласие; анонимная воронка поэтому не равна всему трафику лендинга. Для вошедших пользователей дополнительно смотреть воронку с `studio_opened`, чтобы не смешивать ограничения согласия и интерес к продукту.
2. **Воронка выбора модели.** Шаги: `model_selected` → `quote_shown` → `generation_submitted` → `generation_completed` с `outcome=success`. Разбить по `provider` и `model_id`; сравнивать одинаковые периоды и отдельно смотреть новые/возвращающиеся аккаунты. Если провал между `quote_shown` и `generation_submitted` сосредоточен на одной модели, проверить стоимость, пояснения к цене и ограничения запуска. Это гипотеза, а не доказанная причина.
3. **Удержание.** В Product analytics → Retention задать начальное и возвращающее событие `generation_completed` с `outcome=success`; период «неделя» для возврата за 7 дней и «месяц» для 30 дней. Использовать идентифицированных пользователей; отдельно сравнивать провайдера, первую модель и дату регистрации. Для небольшой когорты показывать абсолютные числа вместе с процентом.

При изменении схемы событий указывать дату версии на панели. Для финансовых выводов сверять агрегации с PostgreSQL: аналитика может запаздывать, быть заблокирована пользователем или содержать повтор доставки.

## Контракт событий для последующей интеграции

События именовать в `snake_case`. Минимальные поля: `schema_version`, стабильный `event_id` (UUID), `occurred_at` в UTC, `channel` (`web`/`telegram`/`server`), `distinct_id`; по наличию — `account_id` в виде непрямого/псевдонимного идентификатора, `session_id`, `request_id`, `job_id`, `provider`, `model_id`. `event_id` передавать в PostHog как `uuid` для повторных доставок. Стабильный `distinct_id` после входа должен связывать действия одного аккаунта на нескольких устройствах. До согласия нельзя создавать или передавать идентификатор аналитики. После выхода сбрасывать идентификацию. При отзыве согласия прекращать отправку и удалять локальный аналитический идентификатор; правила удаления уже собранных данных определить в политике данных.

События браузера считаются удобным сигналом о поведении, а не подтверждением бизнес-операции. Серверное `generation_completed` и кредитные события публиковать из сохранённого изменения состояния через PostgreSQL outbox с неизменными `event_id` и `occurred_at`. Доставщик повторяет отправку с ограниченным backoff; отказ PostHog не останавливает генерацию. Учитывать порядок событий одного `job_id`, идемпотентность и метрику возраста старейшего сообщения outbox. Не экспортировать промпты, исходные файлы, медиа, ответы моделей, cookie, токены, адреса электронной почты, полный текст ошибок и журналы целиком. Для ошибок достаточно безопасного категориального кода.

| Событие | Когда создаётся | Дополнительные поля |
| --- | --- | --- |
| `landing_viewed`, `studio_opened` | первый видимый просмотр лендинга за сессию; явный переход в студию | `entry_point` |
| `login_started`, `login_completed` | начало OAuth; подтверждённая сервером сессия | `auth_provider`, `channel` |
| `mode_selected`, `provider_selected`, `model_selected` | явный выбор пользователем | `mode`, `provider`, `model_id` |
| `quote_shown` | цена успешно показана для актуального выбора | `provider`, `model_id`, `quote_amount_units`, `currency`, `quote_status` |
| `generation_submit_clicked` | нажатие кнопки при валидной форме | `request_id`, `provider`, `model_id` |
| `generation_submitted` | сервер сохранил принятую задачу | `job_id`, `request_id`, `provider`, `model_id` |
| `generation_completed` | сохранён итоговый статус, ровно один раз на переход | `job_id`, `outcome`, `duration_ms`, `error_category` |
| `credits_reserved`, `credits_captured`, `credits_released` | сохранена операция ledger | `job_id`, `amount_units`, `currency` |
| `package_selected`, `checkout_started`, `purchase_fulfilled` | выбор пакета; фактическое начало оплаты; подтверждённое исполнение | `package_id`, `order_id`, `amount_units`, `currency` |

`quote_amount_units` отражает показанную оценку, а не фактическое списание. `generation_submit_clicked` и `generation_submitted` не равнозначны. `generation_completed` содержит `outcome=success|fail|cancelled|unknown`; `unknown` нельзя считать отказом провайдера. Для покупок не включать `checkout_started` до включения реальных способов оплаты.

## Порядок внедрения в продукт

1. На отдельном хосте развернуть архив, создать отдельные production/staging-проекты, выполнить smoke и проверку ClickHouse. До приёмки не отправлять продуктовые данные.
2. Обновить [политику данных](../public/legal/privacy.html): сейчас она говорит, что аналитические cookie не используются. Описать цель, состав данных, срок хранения, согласие, отзыв и права пользователя. Юридический текст согласовать до включения сбора.
3. Добавить фасад с типизированным каталогом событий и allowlist полей. Клиент отправляет события после явного согласия через API AI Media Client. Сервер обогащает их безопасным `distinct_id` и доставляет в PostHog. Autocapture и session replay оставить выключенными.
4. Добавить outbox в PostgreSQL рядом с транзакциями создания задач, изменения статуса и ledger. Реализовать доставщик, повторы, дедупликацию и мониторинг очереди. Начать с новых событий; исторический импорт не нужен.
5. Собрать панели выше и сверить пару конкретных задач/кредитных операций с PostgreSQL. После наблюдения за пропусками расширять каталог событий.

## Если событие не появилось

Проверить согласие и блокировку браузером; наличие серверной сессии и корректного `distinct_id`; ключ **нужного проекта**, URL и HTTPS; ответ capture API; состояние доставщика и возраст outbox; фильтры времени/таймзоны в PostHog. Для серверного события сверить `event_id`, `job_id` и сохранённый статус в PostgreSQL. После синтетического `analytics_smoke` искать событие в Live events, затем проверить таблицу `posthog.events` внутри ClickHouse через Docker-сеть. Если UI показывает событие, а отчёт нет, проверить фильтры, окно воронки и задержку индексации. Не публиковать ClickHouse наружу ради диагностики.

## Ежедневный отчёт и графики: выбранная схема

Для POC выбрана облачная запланированная задача ChatGPT в 09:00 по Москве.
Она получает только фиксированные агрегаты через MCP с OAuth на нашем VPS;
анализ агрегатов выполняется в облаке OpenAI. Подготовка службы, двух панелей
и приёмка описаны в [scheduled-analytics.md](scheduled-analytics.md).
Развёртывание этой службы и фактический облачный запуск ещё не подтверждены.
Продуктовые изменения в AI Media Client этой задачей не выполняются.

## Альтернатива: полностью локальный аналитический агент

После накопления достаточной выборки агент по расписанию читает агрегаты из локального [PostHog Query API](https://posthog.com/docs/api/query) с токеном только на чтение. Он сравнивает одинаковые периоды по воронкам, удержанию, провайдеру/модели, учитывает размер выборки и помечает возможные разрывы данных. Отчёт содержит величину изменения, период, ссылку на сохранённый insight, проверяемые гипотезы и рекомендуемый эксперимент; человек решает, что менять. Модель и расписание работают на нашей инфраструктуре, без передачи сырых событий наружу. Размещённый PostHog MCP не использовать при требовании полностью локальной обработки. Агент не меняет продукт и не получает токен записи.
