# Контракт analytics_daily_report: UX v2

Реализация развёрнута и проверена через подключённый плагин 2026-10-16.
Эндпоинт и MCP-инструмент —
`reporting/server.py`; фиксированные агрегаты — `ux_queries.py`, безопасная
сборка ответа — `ux_report.py`, проекция контракта — `ux_contract.py`.
Приложение AI Media Client, рабочая БД, промпт и расписание не изменены.
Все 22 агрегатных запроса и 8 источников графиков выполнены на живом Query API.
Текущий UX-ответ частичен из-за явных лимитов срезов и размера JSON, без ошибок
запросов. Подробности: [проверка развёртывания](reporting-deployment-2026-10-16.md).

## Совместимость и периоды

Сохранены единственный необязательный параметр `report_day` (полный день из
последних 30 дней), прежние `metadata`, `dashboards`, `data`, `errors`, `complete`.
По умолчанию выбран вчерашний день. Часовой пояс по умолчанию — Europe/Moscow;
существующая серверная настройка сохранена.

`metadata.periods` и `ux.periods` задают UTC-границы полного выбранного дня,
предыдущего дня и семи полных дней перед выбранным. Предыдущий день входит
в семидневную базу. Начало включается, конец исключается. Дневные строки
прежнего отчёта сопоставляются с границами по `day` в `aggregate_periods`.
`models`/`account_users` сохраняют восьмидневный период; `freshness` — период
от начала этого окна до выполнения. Недельные identities вычисляются
независимо, их нельзя получать суммой дневных.

Новый `ux.contract_version=2` добавлен к прежнему ответу. Каждая UX-строка
имеет `period`: report_day, previous_day или baseline, и отдельную sample.
База содержит агрегат семи дней, не среднее дневных identities.
Сравнивайте периоды вместе со зрелостью и изменением покрытия.

## Выборки и срезы

UX считает только schema_version=2 и аккаунтные серверные identities `u_`:

- user_release — основная продуктовая;
- user_debug — отдельная, включая debug_assumed;
- admin_release, admin_debug — администрация;
- admin_preview_release, admin_preview_debug — предпросмотр администратора;
- unknown_population — отсутствующая/неподдерживаемая роль или канал.

Debug не классифицируется как синтетический. В каноническом контракте нет
подтверждённого признака синтетического сценария; такой классификации нет.
Все строки разделены по безопасной версии приложения и viewport_class;
отсутствующие/неподдерживаемые значения представлены unknown и диагностикой.
Где доступны, добавлены mode, provider, фактическая/выбранная модель,
auto/direct, origin, разделы, меню, область клика, действие, исход и категория.
В серверных событиях тип результата берётся из kind, в UI — из mode.
Срезы относятся к событию либо первому событию когорты; они не входят в ключи связи.

| Блок в ux.blocks | Доступные измерения |
| --- | --- |
| journey | Подготовки, попытки (включая несколько в одном flow), принятые задачи, успешные, просмотренные и использованные результаты; identities каждого этапа; технические препятствия; зрелость |
| navigation | Переходы from/to, просмотры/готовность экранов, меню, показы элементов, click_region/element_type, среднее load_time_ms и число образцов; связанное действие после показа |
| model_parameters | Выбор по origin, ручной выбор, mode, выбранная/фактическая модель и provider, auto/direct; снимки initial/clicked/effective; разрешённые параметры, previous/next изменений, происхождение; различия отправленных/эффективных настроек; пустой поиск, закрытие без выбора и активное время списка |
| obstacles_recovery | Категории, показы, затронутые identities и session/category-наблюдения; разрешение, продолжение, продолжение после разрешения; среднее активное recovery_ms и число образцов; technical отдельно |
| history_results | Поиск/пустая выдача, scope, открытие истории, archive/restore и workspace/history-действия по исходам; успешные задачи с просмотром/использованием и download intent; профиль, настройки и очередь по именованным событиям/исходам |

rates указывает numerator, denominator, denominator_unit, percent. При нулевом
или недоступном знаменателе процент null. Для событий знаменатель — независимо
вычисленные события/identities семейства за тот же period/sample; он не строится
по усечённым срезам. Исходы workspace/history показаны отдельно: без ID операции
нельзя связать конкретное started с succeeded. Доля событий семейства не является
конверсией операции. Среднее duration_ms списка — активное время открытие →
закрытие, включая закрытия без выбора, не отдельный timestamp принятого выбора.

## Связи и окно наблюдения

UUID дедуплицируется вместе с distinct_id до расчёта длительностей, попыток и
связей. Число доставок сохраняется. Сырые ключи используются только внутри SQL.

Journey начинается с первого наблюдаемого composer_started для пары
identity/flow_id. Попытка требует matching flow и непустого attempt_id;
generation_submitted — той же identity/sample, flow/attempt и generation_id.
Успех/просмотр/действие связаны с этой задачей и идут во времени последовательно.
Успех одной задачи нельзя сочетать с просмотром/использованием другой.
Несколько попыток не размножают подготовки.

Окно — 48 часов от начала подготовки, включая результаты следующего дня.
Когорта относится к дню начала, не завершения. Запрос читает данные до меньшего
из as_of и конца выбранного дня + 48 часов, затем проверяет индивидуальное окно.
as_of фиксируется один раз. Зрелость наступает после полных 48 часов.
Возвращаются наблюдённые доли всей когорты и отдельные доли зрелой части.
Отсутствие этапа — отсутствие измеренного события, не отказ: UI best effort,
доставка может задерживаться, задача может закончиться позже окна.
Знаменатель preparations включает только наблюдения с flow_id; потерянные ключи
показаны отдельно. Это не регистрация, account activation, retention или
доказательство полезности результата.

Для successful_results когорта начинается с успешного терминального события и
наблюдается 48 часов. Здесь действие измеримо без result_viewed, если UI-показ
потерян; полный journey требует весь префикс.

Использование — result_action, outcome=succeeded, action из copy_result, reuse,
favorite, play. Другие исходы остаются отдельными строками result_events.
download с outcome=started — только намерение; он не включается в used и не
подтверждает сохранение файла. Это консервативное определение отличается от
saved report, допускающего started как признак использования.

Discovery связывает первую видимость элемента и последующее действие в одной
identity/sample/$session_id, до 24 часов. Единица — identity/session/control.
Явные пары: model_picker → model_picker_opened; parameters → parameter_changed
с origin=user; sources → source_action; queue → queue_action; result_actions →
result_action; generate → generation_submit_clicked. ui_clicked не заменяет
эти пары и не измеряет понятность.

Recovery связывает первый показ категории и последующие события той же
identity/sample/$session_id/reason, до 24 часов. Повторные эпизоды одного reason
в сессии объединены: ID эпизода нет. recovery_ms — активное время, не wall time.
Серверные события используют origin_session_id; фоновые завершения не продлевают
UI-сессии и не включаются в UI-продолжение. Технические категории:
models_unavailable, upload, quote_unavailable, service_unavailable, transport_unknown.
Остальные категории — form_or_workflow; отсутствие технического события не
подтверждает доступность сервиса.

Нормализация/восстановление не создают parameter_changed. Ручные изменения
считаются при origin=user; unknown origin не превращается в ноль ручных действий.
Снимки сравниваются по identity/sample/flow/attempt и времени. Разница
clicked/effective измерима, но причина не называется автоматической нормализацией:
такого признака нет. parameter_origins описывает состояние до нормализации.
Доля user origin использует только задачи с известным origin этого параметра.

## Статусы, диагностика и пределы

Прежний complete — успех шести прежних запросов. Для UX проверять отдельно:

- ux.coverage.query_complete: все UX-запросы доступны, без усечения upstream/SQL;
- ux.coverage.complete: дополнительно нет потерь нужных связующих свойств и усечения выдачи;
- status: available, zero_observed, partial или unavailable;
- observed_v2: есть ли v2-события; null при неполной диагностике;
- measurement_is_exhaustive=false: полнота всех реальных действий не гарантируется.

Все пять блоков присутствуют. Каждый содержит доступные rows, failed_queries,
truncated_queries, sample_status, linkage и ненаблюдаемые семьи.
Успешный запрос без строк отличается от unavailable. Zero_observed означает
ноль доставленных событий этого контракта в периоде, не отсутствие активности
и не доказательство включённого сбора.

Диагностика: статус каждого запроса и family/sample, доступность каждого
ожидаемого события, last_event/age_seconds, schema v1/v2/unsupported, UUID/events,
deliveries, identities, missing flow/attempt/generation/UI/origin-session,
присутствие разрешённых свойств (with_*), неподдерживаемые значения срезов,
unrecognized top-level properties только счётчиком, collection_mode
(debug_assumed/unspecified/other) и противоречие debug_assumed с release_channel.
Missing_* нельзя суммировать как уникальные затронутые события.
Период свежести: начало восьмидневного окна → as_of, отдельно от периодов когорт.

16 новых фиксированных запросов выполняются последовательно после шести прежних.
Каждый возвращает до 400 групп; достижение лимита консервативно помечается
truncated. Прежний models сохраняет 100. Upstream hasMore/has_more/is_truncated/next
сохраняются. UX ограничен 512 000 байт компактного UTF-8 JSON: удаляются хвосты
самых больших наборов, блоки становятся partial, добавляются
output_truncated/included_rows. Лимит относится к UX payload без MCP-обёртки и
прежних агрегатов. Общий бюджет — 270 секунд; сетевой timeout ≤45 секунд и
остатка бюджета. Остальные запросы при его исчерпании unavailable.
Тексты ошибок/SQL модели не выдаются. Входной schema инструмента не расширен.

Операторская проверка `python -m reporting.check` по умолчанию завершается
ошибкой при усечении UX. Явный `--allow-truncated` допускает ограниченную
выдачу: печатает `truncated=true`, `complete=false`, но сохраняет ошибку выхода
при сбое запроса или нарушении схемы. Этот флаг не меняет MCP-контракт,
лимиты или статус покрытия публичного отчёта.

## Предупреждения и недостающие измерения

2026-10-09 debug начал сбор без подтверждения: collection_mode=debug_assumed,
release_channel=debug. Рост объёма событий на границе не доказывает рост
использования. Пять saved reports фильтруют user/release, поэтому ноль в них не
доказывает отсутствие debug/admin. Прежние агрегаты смешивают schema v1/v2 и
выборки; UX v2 отделён. Отсутствующий collection_mode не называется автоматически
подтверждённым согласием.

Недоступны: признак синтетического сценария, подтверждение доступного сервиса,
причина нормализации, dedicated advanced_settings action, ID отдельного
препятствия/операции, успех поиска нужного материала, подтверждение сохранения
файла и число свойств, отброшенных до capture. Первые посещения, регистрации,
retention и финансовые выводы не добавлены. Непустой поиск не равен успеху.

## Безопасность и панели

Проверяется точный набор колонок, даже для пустой выдачи. Числа конечны,
счётчики неотрицательны; категории, версии, model ID и значения параметров
валидируются. settings JSON целиком не выдаётся — только агрегаты разрешённых
параметров. Не возвращаются UUID, distinct_id, session_id, flow_id, attempt_id,
generation_id, внутренние IDs, промпты, поисковый текст, названия, URL материалов,
аккаунтные данные и error text. OAuth scopes: query:read/project:read, без изменений.
SQL и свойства недоступны как параметры инструмента.

analytics_dashboard_links и отчёт сохраняют Overview/Journey и добавляют
[UX](https://analytics-195-209-221-217.sslip.io/project/1/dashboard/4).
Ссылки ограничены dashboard URL того же PostHog origin/project.

## Проверки и происхождение

```powershell

```

Тесты исполняют генерируемый production SQL на синтетических событиях через
SQLite с адаптацией HogQL-примитивов. Проверены пустые данные, полный путь,
несколько попыток/следующие сутки/разные задачи, популяции/схемы, UUID-повторы,
потеря UI/ключей, зрелость, сессионные связи, восстановление/нормализация,
поиски/выбор/готовность, download intent, частичный сбой, усечение/JSON limit,
отсутствие сырых данных. Проверен публичный MCP-вызов, независимость complete/UX,
OAuth discovery и 401 без OAuth. Это не живое исполнение HogQL.
Результат 2026-10-10: 41 тест прошёл; 22 Query API payload сверены с Pydantic
schema из закреплённого POSTHOG_VERSION; git diff --check прошёл. Пример выше
автоматически сопоставлен с реальным результатом синтетического расчёта.

query:read токеном: 6 прежних/16 UX-запросов и 8 chart sources должны пройти.
